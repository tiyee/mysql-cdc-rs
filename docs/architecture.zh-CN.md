# 系统如何工作

[English](architecture.md) | 简体中文

[文档目录](README.zh-CN.md)

mysql-cdc 把 MySQL 日志里的数据修改整理成应用可以消费的变更通知。理解它时，可以先看三个问题：谁读取日志、谁判断变更何时生效、谁把结果交给用户。

## 三层分别做什么

| 层 | 负责什么 | 交出的结果 |
| --- | --- | --- |
| mysql-replication | 连接 MySQL 或读取本地 binlog，识别日志中的事件 | 原始 binlog 事件，包含行修改和事务、日志控制信息 |
| mysql-canal | 按库表筛选、识别主键和记录的字段，等待事务提交，管理恢复位置 | 已提交事务中的通用变更通知 |
| Pikachu | 读取产品配置、执行命令、打印结果 | 默认每行一条 JSON |

组件依赖从上到下：**Pikachu → mysql-canal → mysql-replication**。`mysql-cdc-rs` 是统一的 Rust 库入口，方便应用同时使用两个库，不增加处理步骤。整套系统名称是 **mysql-cdc**。

聚合库仅提供 `canal` 和 `replication` 两个模块。`canal::Canal::new` 管理配置来源、处理器和检查点；原始事件消费由复制库的读取器和复制流管理。配置与错误类型也归各模块所有。

## 一次更新怎样到达应用

假设应用把 `app.users` 中主键 42 的姓名改为 Bob：

| 阶段 | 系统做了什么 | 此时用户能否收到通知 |
| --- | --- | --- |
| MySQL 写入日志 | 记录表信息、行修改和事务边界 | 否 |
| 复制层读取 | 识别事件类型，读取修改前后数据 | 原始事件读取方可以看到日志内容 |
| Canal 整理 | 筛选表、确定主键和字段，暂存当前事务 | CDC 消费方还收不到 |
| MySQL 提交事务 | 日志出现提交标记 | Canal 交付整个事务 |
| 处理器成功 | 用户处理完毕，或 CLI 成功写出并刷新输出 | 保存检查点，供下次恢复 |

如果事务回滚，Canal 丢弃暂存的变更。一个事务修改十行，就在提交后按日志顺序交付这十条变更；库的处理器一次收到整个事务。直接读取原始事件的程序需要自行判断事务是否提交。

具体行数据和 MINIMAL/FULL 示例见[事件说明](events.zh-CN.md)。

## 为什么有两种事件

原始事件回答“日志里记录了什么”。它包含格式说明、表结构的编码信息、行修改、事务标记等，适合协议分析和原始数据检查。

通用变更通知回答“哪个来源的哪张表、哪条记录被修改了”。它保留来源、库表、操作、主键、记录的字段名，以及携带历史列定义和 before/after 值的 `fields`。FULL 的每份适用镜像包含全部列，MINIMAL 仅包含日志记录列。

Canal 校验日志值并提供借用字段视图，无需构造应用行对象。事务持有时只复制所需镜像字节，并共享历史列定义。MINIMAL 没有记录的数据不会被补齐，也不会查询当前数据库来猜测历史值。

## 配置为什么逐层包含

| 层 | 自己需要的配置 |
| --- | --- |
| mysql-replication | 连接地址所在的环境变量、复制 ID、TLS、超时、行镜像模式 |
| mysql-canal | 读取哪些表、如何命名来源、检查点位置、事务缓冲上限；同时包含复制配置 |
| Pikachu | 产品自己的设置；同时包含完整 Canal 配置，目前没有额外必填产品项 |

因此产品配置中的每个来源，都通过 `mysql-canal → sources → mysql-replication` 提供连接设置。只使用 Canal 库时，不需要最外面的产品层。完整示例见[配置与运行](configuration.zh-CN.md)。

## 首次启动与恢复有什么不同

**首次启动**会短暂获取 MySQL 全局读锁，记录选中表的结构和当前已提交位置，再开始消费。此位置之前的数据不会补发，系统也不做全量快照。初始化会短暂影响写入，应选择合适的窗口。

**后续启动**从检查点继续，使用检查点保存的历史表结构解释历史日志。系统会核对来源身份和所选库表，避免把某个来源的检查点用于另一个来源。MySQL 必须仍保留这些日志。

**离线回放**使用现有检查点和对应日志文件，不连接 MySQL，也不修改检查点。它适合检查已有日志和复现数据处理过程。

## 多个来源怎样一起运行

每个来源有独立连接、表结构、事务缓冲和检查点。east 的主键 42 与 west 的主键 42 是不同记录，输出中的 `source` 用来区分它们。

同一来源保持日志顺序。共享输出时，一个事务写完再写另一个事务，不会把两个事务的行交错打印。多个实例之间没有统一的全局事件顺序，初始化也不是跨实例的一致快照。

任一来源失败会让本次运行停止，其他来源在事件之间收到停止请求；阻塞读取可能等到超时才返回。重启后各来源从自己的检查点继续。

## 消费方需要处理什么

| 情况 | 结果 | 消费方需要做什么 |
| --- | --- | --- |
| 正常提交并处理成功 | 保存检查点 | 继续处理下一批 |
| 事务回滚 | 丢弃变更 | 不会收到该事务的行通知 |
| 输出成功，但检查点保存前退出 | 重启后可能重复交付 | 让处理逻辑能安全重复执行 |
| 表结构变化或日志不支持 | 停止，不越过未确认数据 | 排查并明确处理表结构和消费起点 |
| 处理速度低于写入速度 | 消费积压，慢处理器会阻塞继续交付 | 监控延迟并保留足够的上游日志 |

CLI 的输出刷新仅说明已写入标准输出或管道，不代表下游已持久化。需要可靠交付时，应用处理器应在保存业务结果后再确认成功。
